# 故障注入与一致性验收

验收日期：2026-09-04。所有结果均来自本机真实请求和数据库/RabbitMQ 状态，不是设计预期的转述。

| 场景 | 故障与步骤 | 最终状态 | 自动恢复 |
|---|---|---|---|
| A 库存后订单失败 | 预占后、订单落库前抛错 | 库存前后不变；预占记录 `RELEASED(30)`；订单数 0 | 是 |
| B 事务后 MQ 不可用 | OrderCreated 已随订单提交，发布端故障 | Outbox `RETRY(20)`、重试 1 次、投影缺失；恢复后 Outbox `SENT(10)`、累计重试 2 次、投影出现 | 是 |
| C 同一支付事件 100 次 | 同一 eventId 发布 100 次 | 订单 `WAIT_DELIVERY/PAID/version=1`；订单消费日志 1；库存确认 1；状态日志 1 | 是，消费幂等 |
| D 支付/关单竞争 | 支付回调成功后立即投递关单 | 订单 `CANCELED(90)`；库存 `RELEASED(30)`；支付单 `PAID(20)`；无“取消但售出”；登记对账异常 | 部分，需退款闭环 |
| E Inventory Consumer 故障 | 消费持续抛错 | 4 次尝试后进入 `inventory.confirm.dlq`，订单已支付、库存仍 RESERVED；恢复后重放原消息，库存确认 1 次，DLQ 清零 | 需人工重放 |
| F Redis 不可用 | 订单服务指向不可用 Redis 端口 | 366 ms 返回 `SYSTEM_BUSY`；库存 `100/93/2/5` 前后不变；无订单、无预占 | Redis 恢复后可继续 |

竞争场景还暴露并修复了取消状态码不一致：状态机使用 90，而旧对账与投影重建 SQL 使用 50。修复后重建能正确得到 `CANCELED`，对账也能识别取消单。

## 尚未闭环

支付已经成功但订单被关单时，目前只登记 `PAY_SUCCESS_AFTER_ORDER_CLOSED`。企业生产版本仍需自动退款、退款幂等、失败重试、人工工单和资金对账闭环。
